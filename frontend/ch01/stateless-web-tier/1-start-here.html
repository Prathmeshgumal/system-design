Chapter 1 · Scale from zero to millions · Stateless web tier

Stateless Web Tier, Start Here

To handle more users you add more web servers. That only works if any server can answer any user. A stateless web tier makes that true by moving each user's session data off the web servers and into a shared store that every server can read.

Stateful: a doctor who keeps your file in their own drawerOnly that doctor can treat you. If they are on leave, nobody else knows your history. If the clinic hires more doctors, they can't help existing patients.
Stateless: files kept in the clinic's central records roomAny doctor can see you. They pull your file, treat you, put it back. Doctors can come and go and patients don't notice.
01 · The word "state"

What is state?

State is anything the server has to remember about you between requests. The most common example is your session: the fact that you are logged in, who you are, maybe your cart. HTTP itself forgets everything after each request, so the server has to store this somewhere. Here is what happens when you log in:

  1. You log in. The server checks your password.
  2. The server creates a session and stores it somewhere.
    session abc123 → { user: "A", loggedIn: true, cart: ["shoes"] }
  3. It sends you a cookie holding only the session ID. Your browser keeps it.
    Set-Cookie: session_id=abc123
  4. Every later request carries that cookie. The server looks up abc123 to know who you are.
    GET /cart   Cookie: session_id=abc123

The whole topic is about one question: where is the session from step 2 stored? Inside one web server's memory (stateful), or in a shared store outside the web servers (stateless)?

03 · The problem

Why stateful servers get in the way

In a stateful design, every request from User A must go to Server 1, because only Server 1 has A's session. Load balancers can do this with sticky sessions: they remember which server each user belongs to. The book says this works but adds overhead, and three things get hard:

Adding servers

A new server starts with no sessions. Existing users stay stuck to their old servers, so the new one only helps new users. Load stays uneven.Lab mission 5

Removing servers

To shut a server down, you have to move or drop the sessions on it. Its users get logged out.Lab mission 4

Server failures

If a server crashes, every session in its memory is gone. All its users are suddenly logged out and lose their carts.Lab mission 4
04 · The fix

Move the state out

Keep sessions in a shared data store that all web servers can reach. The book lists the options: a relational database, Memcached or Redis, or NoSQL. In its design it picks NoSQL because it is easy to scale. Now each web server is interchangeable: it receives a request, reads the session from the store, does the work, and forgets.

That unlocks autoscaling: adding web servers automatically when traffic rises and removing them when it falls. Since no server holds anything unique, adding or removing one never logs anybody out. This is Figure 1-14:

05 · Compare

The two designs at a glance

StatefulStateless
Where sessions liveInside one web server's memoryIn a shared store (NoSQL, Redis, SQL)
Which server can answer User AOnly A's serverAny server
Load balancerNeeds sticky sessionsCan send each request anywhere
Server crashesIts users are logged outNobody notices; others take over
Adding serversHelps only new usersHelps everyone right away
AutoscalingHardEasy
CostNo extra lookupOne extra network call to the store per request, and the store must be fast and reliable

The trade-off to mention in interviews: stateless moves the problem, it doesn't delete it. The session store is now something every request depends on, so it must be fast (Redis, NoSQL) and replicated so it doesn't become a single point of failure.

06 · Vocabulary

Words you will hear

State
Data a server must remember about a user between requests.
Session
The most common state: who you are, that you are logged in, your cart.
Session ID / cookie
A random ID stored in your browser and sent with every request so the server can find your session.
Stateful server
Keeps users' state in its own memory, so a user must keep coming back to it.
Stateless server
Keeps no user state. Reads it from a shared store on each request.
Sticky sessions
A load balancer feature that always sends the same user to the same server.
Horizontal scaling
Handling more traffic by adding more servers (scale out), rather than a bigger server (scale up).
Autoscaling
Adding or removing servers automatically based on traffic.
