Chapter 1 · Scale from zero to millions · CDN

CDN, Start Here

A CDN (content delivery network) is a set of cache servers spread around the world. Each one keeps copies of your site's static files, so a user downloads them from a server nearby instead of from your own server, which may be on another continent.

Without a CDNEvery customer in the world orders from one warehouse in Virginia. A customer in Mumbai waits for the parcel to cross the planet, every time.
With a CDNPopular items are stocked in local warehouses in many cities. The Mumbai customer gets theirs from the Mumbai warehouse. Only items it has never stocked come from Virginia.
01 · The problem

Distance is the slow part

You already know a cache from earlier in the chapter: keep a copy close by so you don't redo slow work. A CDN uses the same idea, but the slow thing it avoids is distance. Data travels through fibre at about 200,000 km per second. That sounds fast, but a webpage needs many round trips, and each one pays the full distance there and back.

Pick a city to be the user. The site's origin server is in Virginia, USA.

Rough model: round trip = distance × 2 × 1.5 (cables don't run straight) ÷ 200 km per ms. Loading the static files on a typical page takes about 10 round trips: 3 to set up a secure connection, then about 7 rounds to fetch around 40 files over 6 parallel connections. Real numbers vary, but the gap is real.

02 · Scope

What a CDN keeps: static files

The book focuses on static content: files that are the same for every user. Content built per user is dynamic. Caching dynamic content on a CDN exists, but the book calls it out of scope.

05 · Trade-offs

Four things to think about

The book lists these under "Considerations of using a CDN". Interviewers like to ask about them because they show you understand the costs, not just the benefits. Each one has a mission in the lab.

Cost

A CDN is a paid third-party service, charged for data moving in and out. A file that is rarely requested will usually have expired before the next person asks, so you pay without getting cache hits. Keep rarely used files off it.

Cache expiry (TTL)

Too long, and users see an old file after you change it. Too short, and edges keep going back to the origin, which loses most of the benefit. Pick the TTL based on how often the file changes.Lab missions 4 and 5

CDN fallback

CDNs can go down too. Your app should notice that the CDN is not answering and fetch the files from the origin instead. Slower, but the site still works.Lab mission 8

Invalidating files

To replace a file before its TTL runs out, either call the CDN vendor's invalidation API to drop it, or use object versioning: change the URL to image.png?v=2. A new URL is a new cache key, so every edge fetches the new file.Lab missions 6 and 7
06 · Vocabulary

Words you will hear

Origin
Your own server or storage (for example Amazon S3) that holds the real copy of every file.
Edge / PoP
A CDN server in a particular city. PoP means "point of presence". Big CDNs have hundreds.
Cache hit
The edge already has a fresh copy and returns it right away.
Cache miss
The edge has no copy, or its copy expired, so it fetches from the origin first.
TTL
Time to live. How long the edge may keep a copy. The origin sets it, usually with Cache-Control: max-age=3600 (one hour).
Stale
A cached copy that is older than the file on the origin.
Invalidate
Tell the CDN to delete its copy now, before the TTL runs out.
CDN domain
The URL users load files from, such as mysite.cloudfront.net/logo.jpg on Amazon CloudFront or mysite.akamai.com/... on Akamai.
07 · Doubts

Questions from our doubt session

These came up while learning this topic. Each one is a common place to get confused, and a common interview follow-up.

How is a CDN different from a server?

A CDN is servers too. The difference is their job. Your server (the origin) is yours, sits in one or a few places, holds the real copy of everything, and runs your code: login, cart, database queries. CDN edge servers belong to a vendor, sit in hundreds of cities, hold only copies of static files, and run none of your logic. On a miss, they copy the file from your origin.

Origin = the publisher with the master copy. CDN = bookshops in every city stocking copies. A CDN can't work without an origin.

How is a CDN different from a cache?

A CDN is a cache, one kind of it. Chapter 1 adds two caches that do different jobs on opposite sides of your web server.

Cache tier (Redis, Memcached)CDN
StoresData: query results, profilesFiles: images, CSS, JS, video
SitsIn your data centre, next to web serversNear users, in many cities
Called byYour web server codeThe user's browser
ProtectsThe databaseWeb servers, and users from distance
Filled byYour code, after a database readThe edge itself, on a miss
 
User ──► CDN (files, near the user)
  │
  └──► Load balancer ──► Web server ──► Cache tier (data) ──► Database

A CDN caches files near users, so web servers do less work. A cache tier caches data near the web servers, so the database does less work.

What is TTL?

Time To Live: an expiry timer on a cached copy. The origin sets it with a header such as Cache-Control: max-age=3600 (one hour). Until the timer runs out, the edge serves its copy without asking the origin. After that, it throws the copy away and fetches a fresh one on the next request.

TimeAt the Mumbai edge, TTL = 1 hour
10:00Miss. Fetch from origin, store copy until 11:00
10:05Hit. Served from the edge
11:00TTL runs out. Copy removed
11:02Miss. Fetch fresh copy, store until 12:02

Too long: users see an old file after you change it. Too short: most requests go back to the origin. Files that rarely change get long TTLs.

TTL is 1 hour and I change the file after 5 minutes. Do users see the old file for 55 minutes?

Yes, unless you do something. TTL doesn't prevent old data. It limits how long old data can last. The edge never checks whether the origin changed. To make a change show up early, there are two options:

Invalidate (purge)Versioned URL
HowDeploy script calls the vendor API: "delete /logo.png everywhere"New file gets a new URL: logo.png?v=2 or logo.7be240.png
SpeedSeconds to minutes to reach every edgeInstant. No cache has the new URL yet
Browser cachesNot cleared. Users may still have the old copyCovered. The old URL is no longer requested
Origin loadEvery edge misses at once after a purgeNormal
CostVendors limit or charge for purgesFree

With versioned URLs you can give static files a very long TTL (even a year), because a change always means a new name. The HTML page can't be versioned since users type mysite.com, so it gets a short TTL or skips the CDN, and it points to the latest file names.

Interview line: "TTL bounds staleness. For instant updates I'd use versioned file names with a long TTL, keep HTML on a short TTL, and use the purge API only for emergencies."
